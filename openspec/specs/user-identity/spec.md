# user-identity Specification

## Purpose

Establishes who is making each request, as vouched for by the identity-aware proxy in front of the app. It also
keeps the app's own user accounts linked to the sign-in providers' stable account ids, and tells people when their
sign-in can't be accepted.

## Requirements

### Requirement: Requests are identified by the proxy's signed token
Every API request SHALL carry a valid Cloudflare Access JWT, checked for its signature against the team's public
keys, its issuer, audience and expiry. A request without one SHALL be rejected with 401 and SHALL NOT read or
change any data. Identity headers that aren't signed, such as the plain email header, SHALL NOT be trusted.

#### Scenario: Valid token
- **WHEN** an API request carries a valid Access JWT
- **THEN** the request runs as the user that token identifies

#### Scenario: No token
- **WHEN** an API request carries no Access JWT
- **THEN** the response is 401 and nothing is read or changed

#### Scenario: Forged email header
- **WHEN** a request carries only a `Cf-Access-Authenticated-User-Email` header naming an existing user
- **THEN** the response is 401

#### Scenario: Token that fails a check
- **WHEN** a token is signed by another key, is for another audience or issuer, or has expired
- **THEN** the response is 401

### Requirement: The app page loads without an account
The client's page and static files SHALL be served to any request without an account check, so a person whose
sign-in is refused still gets a page explaining why. They contain no receipt or user data.

#### Scenario: Refused sign-in still loads the page
- **WHEN** a person whose sign-in is refused opens the app
- **THEN** the page loads and shows the sign-in problem page

### Requirement: Users have their own ids, linked to external identities
Each user SHALL have an id generated by the app, independent of any provider. A user SHALL be linked to at most
one external identity per supported provider. An external identity is the provider and its stable account id,
and SHALL belong to at most one user. A user's email is optional and unique among users when present.

#### Scenario: Ids are the app's own
- **WHEN** a user is created
- **THEN** their id is generated by the app, not taken from the provider's account id or the email

### Requirement: The full identity is looked up once per proxy session
For a request whose Access session hasn't been seen, the app SHALL look up the full identity from the proxy: the
sign-in method, the provider's stable account id and the name. It SHALL reuse the result for the rest of that
session instead of looking it up on every request.

#### Scenario: Repeat requests in one session
- **WHEN** a signed-in user makes several requests in the same Access session
- **THEN** the identity is looked up at most once for that session

### Requirement: Only supported sign-in methods are accepted
The app SHALL accept only the sign-in methods it supports, currently Google personal and Workspace accounts.
Any other method SHALL be refused with 403 and an `unsupported-sign-in` problem, and no user SHALL be created
or changed. The response SHALL NOT name the supported providers.

#### Scenario: Unsupported method
- **WHEN** someone signs in to Access with a method the app doesn't support
- **THEN** API requests get 403 with an `unsupported-sign-in` problem, and no user is created

### Requirement: The first sign-in creates a user
When no user is linked to the request's external identity and no user holds its email, the app SHALL create a
user with that email and name, linked to that external identity.

#### Scenario: New person
- **WHEN** a person signs in for the first time with an email no user holds
- **THEN** a user is created with their email and name, linked to their external identity

### Requirement: Returning users are found by their external identity
A user linked to the request's external identity SHALL be that request's user, whatever email the token carries.
The app SHALL update the user's name, and their email when it changed and no other user holds the new one. When
another user holds it, the stored email SHALL stay unchanged and a warning SHALL be logged.

#### Scenario: Email changed at the provider
- **WHEN** a linked user signs in with a new email that no other user holds
- **THEN** they get the same user, with their receipts, and the stored email is updated

#### Scenario: New email held by another user
- **WHEN** a linked user signs in with a new email that another user holds
- **THEN** they get their own user, both users' emails stay unchanged, and a warning is logged

#### Scenario: Name changed at the provider
- **WHEN** a linked user signs in with a different name
- **THEN** the stored name is updated

### Requirement: An email held by another account is refused
When no user is linked to the request's external identity but another user holds its email, the sign-in SHALL be
refused with 403 and an `account-conflict` problem. Nothing SHALL be created or linked, so no one gains access to
another account's receipts by email.

#### Scenario: Same email, different external identity
- **WHEN** someone signs in whose email belongs to a user linked to a different external identity
- **THEN** API requests get 403 with an `account-conflict` problem, and no user or link is created

### Requirement: An unavailable identity lookup refuses new sessions
When the full identity can't be looked up, the app SHALL answer 503 with an `identity-unavailable` problem
instead of guessing the user from the email. The lookup SHALL be retried on a later request. Sessions already
identified SHALL keep working.

#### Scenario: Lookup fails
- **WHEN** a new session's identity lookup fails
- **THEN** the response is 503 with an `identity-unavailable` problem, and a later request tries again

#### Scenario: Existing session during the outage
- **WHEN** the identity lookup is failing and a user whose session was already identified makes a request
- **THEN** the request succeeds

### Requirement: Admins are configured by email
A user SHALL be an admin when their account's email matches an entry in the configured admin list, ignoring case.
The list is read from configuration, not stored per user. An email in the token that another user holds SHALL NOT
make anyone an admin.

#### Scenario: Listed email
- **WHEN** a user whose email is in the admin list, in any letter case, makes a request
- **THEN** they are treated as an admin

#### Scenario: Unlisted email
- **WHEN** a user whose email is not in the admin list makes a request
- **THEN** they are treated as a member

#### Scenario: Admin email held by another user
- **WHEN** a linked user signs in with an admin's email that the admin's user still holds
- **THEN** they keep their own email and are treated as a member

### Requirement: Admins can release an email
An admin SHALL be able to release an email, which clears it from the user holding it. That user keeps their
external identity, name and receipts. Within a minute, the person refused for that email SHALL be able to sign
in and get a new user. Members SHALL get 403, and an email no user holds SHALL give 404.

#### Scenario: Resolving a conflict
- **WHEN** an admin releases an email that caused an `account-conflict`, and that person signs in again a minute later
- **THEN** a new user is created for them, and the previous holder keeps their receipts without an email

#### Scenario: Member tries to release
- **WHEN** a member calls release email
- **THEN** the response is 403 and nothing changes

#### Scenario: Unknown email
- **WHEN** an admin releases an email no user holds
- **THEN** the response is 404

### Requirement: The client can read the signed-in user
`GET /api/me` SHALL return the signed-in user's id, email, name, whether they are an admin and the sign-out URL.
The sign-out URL is null when there is nothing to sign out of, as in development. A refused sign-in SHALL get the
same problem response as any other API call.

#### Scenario: Signed-in member
- **WHEN** a signed-in member calls `GET /api/me`
- **THEN** it returns their id, email, name, `isAdmin: false` and the Access sign-out URL

### Requirement: Development signs in a configured user
In the Development environment, when a development user email is configured, every request SHALL be signed in as
that user without the proxy. Outside Development the app SHALL refuse to start if a development user is
configured, or if the proxy's team domain or audience is missing.

#### Scenario: Development user
- **WHEN** the app runs in Development with a development user configured
- **THEN** requests are signed in as that user without an Access token

#### Scenario: Development user in production
- **WHEN** the app starts outside Development with a development user configured
- **THEN** it logs why and exits with code 1

#### Scenario: Missing proxy settings
- **WHEN** the app starts outside Development without the Access team domain or audience
- **THEN** it logs why and exits with code 1

### Requirement: The header shows the signed-in user
The header SHALL show the signed-in user as an avatar with their initials (from the name, or else the email). It
SHALL open, on click or keyboard, a menu with the name, email, an admin badge for admins and Sign out. The menu
SHALL work at phone width and in both color schemes.

#### Scenario: Opening the account menu
- **WHEN** a signed-in user clicks or taps their avatar
- **THEN** a menu shows their name, email, an admin badge if they are one, and Sign out

#### Scenario: No sign-out URL
- **WHEN** the signed-in user has no sign-out URL
- **THEN** the menu has no Sign out item

### Requirement: Sign-in problems replace the app with an explanation
When any API call shows the sign-in can't be used, the app SHALL show a full page in place of the app. The page
explains the problem without naming any provider and offers one action: Sign out for an unsupported method or an
account conflict, Try again when the identity is unavailable, and Sign in again when the Access session expired.

#### Scenario: Account conflict
- **WHEN** `GET /api/me` answers with an `account-conflict` problem
- **THEN** the page says the email belongs to another account and to ask an admin, and offers Sign out

#### Scenario: Unsupported method
- **WHEN** an API call answers with an `unsupported-sign-in` problem
- **THEN** the page says the sign-in method isn't supported, without naming any provider, and offers Sign out

#### Scenario: Identity unavailable
- **WHEN** an API call answers with an `identity-unavailable` problem
- **THEN** the page says the account couldn't be confirmed and offers Try again, which reloads the app

#### Scenario: Session expired
- **WHEN** an API call is redirected by the proxy to its sign-in page
- **THEN** the page says the user was signed out and offers Sign in again, which reloads the app

### Requirement: Admins can list users
An admin SHALL be able to list every user with their id, email and name, sorted by name and then email. A user
whose email was released is listed with a null email. Members SHALL get 403.

#### Scenario: Admin lists users
- **WHEN** an admin lists users after two members and the admin have signed in
- **THEN** all three are listed with their ids, emails and names, sorted by name

#### Scenario: Released email
- **WHEN** an admin lists users after releasing a user's email
- **THEN** that user is still listed, with a null email

#### Scenario: Member tries to list
- **WHEN** a member lists users
- **THEN** the response is 403
